# PLAY_02_ECONOMIC_ENGINE_REVIEW.md

## 1. 개요
본 문서는 `PLAY_02_ECONOMIC_ENGINE.md`에 명시된 경제 엔진 설계안을 현재 RealRankus 코드베이스(프론트엔드 중심의 Firebase BaaS 구조)에서 구현할 때 발생할 수 있는 기술적 제약, 충돌 가능성, DB 요구사항 및 모호한 부분을 분석한 리뷰 결과입니다.

## 2. 기존 아키텍처와의 기술적 충돌 및 제약

### 2.1 Batch 기반 타이머 및 스케줄러의 부재
*   **요구사항**: `1 real day ≈ 4 simulated months` 비율로, 유저의 온/오프라인 여부와 무관하게 경제 환경과 플레이어 상태가 업데이트되는 Batch 실행 모델.
*   **기술적 충돌**: 현재 RealRankus는 순수 프론트엔드(Client-Side) 구동 방식이므로, 사용자가 브라우저를 닫으면 백그라운드 연산이 불가능합니다.
*   **해결 방향**: 반드시 서버 사이드의 스케줄러(예: Firebase Cloud Functions의 `pubsub.schedule` + Cloud Scheduler, 혹은 외부 서버의 Cron Job)가 필요합니다.

### 2.2 대규모 상태 업데이트(Batch Update) 한계
*   **요구사항**: 매 Batch마다 모든 플레이어의 자산, 부채, 현금흐름, 경제 지표, 부동산 가격 등을 재계산하고 업데이트.
*   **기술적 제약**: Firebase Firestore를 사용할 경우, 단일 트랜잭션/배치 쓰기(Batch Write)의 한도는 500개 도큐먼트입니다. 플레이어 수가 수천~수만 명 단위로 넘어갈 경우 단일 Cloud Function 인스턴스의 실행 시간 제한(최대 9분)이나 메모리 제한, 쓰기 한도를 초과할 수 있습니다.
*   **해결 방향**: 대용량 데이터를 처리하기 위한 분산 워커(Distributed Worker) 구조나 Chunk 단위의 페이징 배치 처리를 설계해야 합니다.

### 2.3 클라이언트-배치 간 동시성(Concurrency) 문제
*   **요구사항**: 플레이어는 Decision Window를 통해 실시간으로 Buy/Sell 요청을 서버로 전송합니다.
*   **기술적 충돌**: 서버의 일일 Batch(예: 자정 00시 실행)가 모든 유저의 상태를 업데이트하고 있는 도중에, 유저가 매수(Buy) 트랜잭션을 요청할 경우 상태(Cash, Debt 등)가 충돌(Race Condition)할 수 있습니다.
*   **해결 방향**: Batch가 실행되는 짧은 시간 동안 트랜잭션을 일시 정지(Lock) 시키거나, Firestore 트랜잭션을 통해 낙관적 락(Optimistic Lock) 처리를 철저히 구현해야 합니다.

## 3. 계산상 문제 및 고려사항

### 3.1 JavaScript 부동소수점 정밀도 문제
*   **이슈**: 부동산 가격, 대출 이자 등은 수억~수백억 단위의 큰 숫자와 세밀한 이자율(예: 3.25%)이 곱해집니다. Node.js나 브라우저의 기본 `Number` 타입(IEEE 754 64비트 부동소수점)을 사용할 경우 계산 및 반올림 오차가 발생할 수 있습니다.
*   **권장사항**: `BigInt`를 사용하거나 `decimal.js`, `big.js` 같은 고정밀도 수학 라이브러리를 통해 금전 계산을 처리해야 합니다.

### 3.2 음수 현금흐름(Negative Cash Flow) 처리 모호성
*   **이슈**: 소득보다 지출(생활비+이자 등)이 커서 현금이 0 미만으로 떨어지는 상황에 대한 기계적인 처리 방식이 완전히 확정되지 않았습니다. 강제 매각(Forced Sale)은 MVP에서 제외되었으나, Cash가 음수가 될 때 이를 자동으로 마이너스 통장(추가 대출)으로 전환할지, 아니면 단순 상태값으로 둘지에 대한 명확한 규칙이 필요합니다.

## 4. 데이터베이스(DB) 요구사항

향후 `PLAY_03`에서 설계될 DB 스키마에 반드시 반영되어야 할 사항들입니다.

*   **히스토리(TimeSeries) 데이터 보존**: Decision Log뿐만 아니라, `PLAY_ECONOMIC_STATE`와 `PLAY_PROPERTY_STATE`의 과거 스냅샷을 저장해야 합니다. (플레이어가 과거의 어떤 상황에서 의사결정을 내렸는지 맵핑하기 위함)
*   **Read/Write 분리**: 프론트엔드가 조회하는 데이터(`PLAY_PLAYER_STATE` 등)와 서버 스케줄러가 기록하는 영역을 보안 규칙(Security Rules)으로 엄격히 통제해야 합니다.
*   **Seed 기반 재현성**: 렌덤 이벤트나 가격 변동 폭이 적용될 경우, 해당 Batch에 사용된 `random_seed`와 `rule_version`을 Season Log에 필드 단위로 명확히 저장해야 합니다.

## 5. 구현상 모호한 부분 (기획적 결정 필요)

1.  **초기 자산 7억 원의 유동성 범위**: 7억 원이 순수 'Cash'인지, 아니면 초기 거주 주택을 포함한 가치인지 명확히 해야 합니다. (문서상 Cash로 명시되었으나, 현실적 시뮬레이션을 위해 주거 비용(월세/전세)이 처음부터 빠져나가는 구조인지 확인 필요).
2.  **가격 업데이트(Property Price Engine)의 갱신 범위**: 매 Batch(현실의 하루)마다 모든 단지(수천~수만 개)의 가격을 갱신하는 것은 연산량이 과도할 수 있습니다. 거래가 일어나는 단지나 특정 인덱스에 연동되어 가상으로 갱신될지에 대한 범위 지정이 필요합니다.
3.  **LTV/DSR의 실시간 평가**: 대출 상환 시 원리금이 나갈 때마다 DSR을 재평가하여 대출 한도가 실시간 변동되는지, 아니면 대출 실행(Buy) 시점에만 검증하는지에 대한 시점 확정이 필요합니다.
